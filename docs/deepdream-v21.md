# DeepDream v21 ── 重さと再変換

最終更新: 2026-08-22
関連: `docs/video-findings.md`

---

## 0. まず構造を変えた

v18/v19/v20 は、**v17のソースを実行時に `fetch` して文字列置換し `eval` する**作りだった。

```js
const source = await fetch('./main-v17.js').then(r => r.text());
if (!source.includes(oldLoss)) throw new Error('v20: reviewed v17 loss block was not found');
...
(0, eval)(patched);
```

これだと:

- **エラーが出ても行番号が出ない。**「再変換でエラーになる」の中身が読めないのはこれが原因
- v17を一文字でも直すと `includes` が外れて起動しなくなる
- デバッガもソースマップも効かない

v21 では二つに分けた。evalはしない。

| ファイル | 役割 |
|---|---|
| `deepdream/dream-engine.js` | 処理の本体。DOMに触らない。**だから単体で試験できる** |
| `deepdream/main-v21.js` | 画面・モデル読み込み・メモリ管理 |

旧版9本は `archive/deepdream-versions/` へ移した（消していない）。

## 1. 重すぎる問題

### 原因

v20 は入力を縮小せず、原寸のまま全オクターブを回していた。

```js
// No WEBGL_MAX / CPU_MAX downscale. Pad only, never shrink the source.
base = padToTileGrid(input);
```

スマホ写真（4032×3072）で何が起きるか、実装から計算した:

| octave | タイル数 | step | 計 |
|---|---|---|---|
| 1344×1056 | 154 | 18 | 2,772 |
| 1824×1344 | 266 | 14 | 3,724 |
| 2304×1728 | 432 | 10 | 4,320 |
| 3072×2304 | 768 | 6 | 4,608 |
| 4032×3072 | 1,344 | 3 | 4,032 |
| | | **合計** | **19,456回** |

1回30msでも**9.7分**、80msなら**26分**。

メモリも、4032×3072のfloat32テンソルが1枚142MB。処理中は7枚前後を同時に持つので
**約1GB**をGPUに要求する。モバイルGPUには載らない。

### 対処 ── 差分だけを原寸に戻す

DeepDreamは原寸で回す必要がない。作業解像度で夢を見て、
**その差分（detail）だけを原寸に拡大して原画像に足す**。

```
原画像(4032×3072) ──縮小──> 作業(1024×780) ──夢──> 夢を見た結果
                                    │                      │
                                    └──── 差 ───────────────┘
                                          detail
原画像(4032×3072) + 拡大(detail) = 出力(4032×3072)
```

原画像の細部はそのまま残るので、**解像度は落ちない**。
v17のように「288pxの結果を1400pxに引き伸ばす」のとは別物である。

### 実測（実装から算出）

スマホ写真 4032×3072:

| | タイル勾配 | 画素換算 | |
|---|---|---|---|
| v20 | 19,456回 | 179.3M | |
| v21 軽い | 270回 | 10.0M | **18.0倍軽い** |
| v21 標準 | 418回 | 15.4M | **11.6倍軽い** |
| v21 濃い | 396回 | 26.0M | 6.9倍軽い |

タイルが 96px → 192px になった分1回は重いので、**画素換算**で比べている。
回数だけ見ると47倍になるが、それは誇張なので採らない。

### ついでに絵も良くなる

96pxタイルだと mixed5 の特徴マップが **4×4** しかない。
mixed5のユニットの受容野は100px超あるので、1タイルにつき実質1〜2セルしか動かない。
だから模様が育たず、低周波のモヤになる。

192pxで **10×10**、256pxで **14×14**。Google の原典は512pxを使っていた。

## 2. 再変換でエラーになる問題

### 原因

tfjs の `WEBGL_DELETE_TEXTURE_THRESHOLD` は **既定が -1**、つまり
「使い終わったテクスチャを解放せず、再利用のためプールに残す」。

一回目で確保した約1GB分がプールに残ったまま二回目が始まる。
オクターブごとに形が違うので再利用されず、新しく確保しにいく。
そこでGPUメモリが尽きるか、WebGLコンテキストが飛ぶ。

そして v20 は eval で動いていたので、**そのエラーが何行目のどれなのか出なかった**。

履歴も効いている。`pushHistory` は無条件に8枚まで持つ。
原寸4032×3072のImageDataは1枚47MB。8枚で**376MB**。

### 対処

```js
tf.env().set('WEBGL_DELETE_TEXTURE_THRESHOLD', 0);   // 使い終わり次第すぐ解放
tf.env().set('WEBGL_FORCE_F16_TEXTURES', true);      // テクスチャを半分に
```

なお、TensorFlow.js の `tf.disposeVariables()` は「全Variableを破棄」するAPIなので、モデルを再利用するこの画面では使わない。v21初稿では後始末として呼んでいたが、これは2回目の変換を壊すため削除した。

- 履歴を「枚数」ではなく**バイト数（96MB上限）**で持つ
- **`tf.disposeVariables()` は変換後に呼ばない**。LayersModel の重みまで破棄するため、モデルを保持したまま2回目を実行すると壊れる。モデル破棄は `dreamModel.dispose()` に限定する。
- `webglcontextlost` を拾って、黙って死なずにモデルを作り直す
- 状態表示に `tf.memory()` を出す。**テンソル数とGPUバイト数が画面で見える**

### 捨て漏れを機械で測った

「二回目で落ちる」の正体はテンソルの捨て漏れなので、それを試験できるようにした。
tfjs の最小スタブ（確保と破棄だけ追跡する偽物）を作り、エンジンを3回連続で回した。

```
=== 12MPの画像で2回続けて変換する ===
  1回目: 出力 4032×3072 / タイル勾配 418回 / 残存テンソル 0→0 （捨て漏れなし）
  2回目: 出力 4032×3072 / タイル勾配 418回 / 残存テンソル 0→0 （捨て漏れなし）
  3回目: 出力 4032×3072 / タイル勾配 418回 / 残存テンソル 0→0 （捨て漏れなし）

=== 中断しても捨て漏れないか ===
  21タイルで中断 / 戻り値 ImageData（途中結果） / 残存 0→0 （捨て漏れなし）
```

### この試験が実際にバグを1つ掴んだ

中断したときに `padded` と `rows` を**二重に破棄**していた。
中断分岐の中で捨て、`finally` でもう一度捨てていた。

```
Error: 二重破棄 tensor#13830
    at tiledStep (dream-engine.js:140)
```

後始末は `finally` に一本化して直した。
**停止ボタンを押すと落ちる**という別のバグが、これで潰れている。

## 3. ついでに直したもの

前回の所見で挙げて未対応だったもの。

**縦横比の崩れ** ── v20 は縦横それぞれ独立にタイル境界へ切り下げていた。
5:1の帯画像だと、オクターブによって比が 1.94 まで崩れていた。

```
5:1帯  元5.000 → 各octave 4.974 , 5.005 , 4.995   （v21）
```

**タイルの継ぎ目** ── ずらし幅が16pxしかなく、96pxタイルの1/6。
境界がほぼ固定位置に残していた。v21はタイル一枚ぶんまでずらす。

**EXIFの向き** ── `createImageBitmap(file, {imageOrientation: 'from-image'})`。
指定しないと機種によって横倒しになる。

**PNG保存** ── `toDataURL` は原寸だと数十MBの文字列になり端末が固まる。`toBlob` に変更。

**残り時間の表示** ── 何分かかるか分からないと、固まったと思われる。

## 4. 使い方

画面上部に「重さ」が三段階ある。

| | 作業解像度 | タイル | 段数 |
|---|---|---|---|
| 軽い | 768px | 192px | 3 |
| 標準 | 1024px | 192px | 4 |
| 濃い | 1280px | 256px | 4 |

16MP以下の入力では出力は**原寸**。48MP級など16MPを超える入力は、モバイルメモリ保護のため読み込み時に16MP以下へ縮小する。作業解像度は模様の細かさと処理時間だけを決める。
