## 0. この文書の役割

この文書は、配信アーカイブの処理・切り抜き動画化・VRM動画化を行う際の恒久ルールである。

---

## 1. 最重要原則

### 1-1. 嘘の同期をしない
- 字幕タイミングを勘で置かない。
- 要点テロップを字幕の代わりに使う場合は「字幕」ではなく演出テロップとして扱う。
- 単語や文の同期が必要な動画では、Whisper等の実タイムコードを基準にする。
- 前後のズレを手動補正する場合も補正理由を明示する。

### 1-2. 実音声を必ず使う
- 話者本人の配信切り抜きは必ず元配信の実音声を使う。
- 別音声、仮音声、代替読み上げ、無音での仮動画を完成品扱いしない。

### 1-3. 未完成物を完成品扱いしない
- 草案、動作確認、モック、検証用はそのように明記する。
- 「できた」と言うのは目的達成条件を満たした時だけ。
- GitHubへ保存したと言う前に必ず再読して確認する。

### 1-4. ユーザーの指摘が正しければ即検証する
- 字幕がズレている。
- 口が動いていない。
- Tポーズである。
- 内容が違う。
- GitHubに入っていない。

防御ではなく現物確認を優先する。

## 2. 配信アーカイブ正本ルール

### 2-1. 150以降の正本は3層

配信1本ごとに最低限、次の3層を残す。

```text
archive/<回>/raw/part-XX.md
archive/<回>/clean/part-XX.md
reports/<回>.md
```

1. **raw**: ASR由来の原文保存層
2. **clean**: 全文を保った最小校正版
3. **report**: 理論・観測・方法論・運用更新の抽出

`knowledge/` や `video-ideas` は横断利用の二次層であり、各回の正本3層とは分ける。

### 2-2. raw の扱い
- raw は後段処理で上書きしない。
- 明白なASR誤認識があっても原則そのまま保持する。
- 発言内容・順序を保存する。

### 2-3. clean の扱い
- 配信全文を維持する。要約しない。
- 文脈上ほぼ確実なASR誤変換だけ直す。
- 数字前後の崩れ、確定用語、明白な固有名詞誤認識を補正する。
- 不明な箇所を創作しない。必要なら `[聞き取り不明]` とする。
- raw と clean は保存経緯によって part の分割位置・分割数が違ってもよい。連結時の全文対応を優先する。

### 2-4. report の扱い
- 配信の短い要約を含める。
- 本人の独自理論、観測、方法論、運用更新を抽出する。
- 個別相談の人物評・予言を、そのまま一般理論へ昇格させない。
- 医学・歴史・宗教・科学上の事実検証は、発言記録と分離する。

### 2-5. 旧形式を再作成しない

以下は main 上の正本として廃止済み。

- `transcripts/YYYY/MM/`
- `reports/YYYY/MM/`
- `*-original.md`
- `*-readable.md`
- `*-semantic-translation.md`
- `*-meaning-extraction.md`

必要ならGit履歴から参照する。main に復活させない。

### 2-6. 相談内容の扱い
- 相談者の個人情報、病歴、関係性、住所推定、アカウント特定情報は公開向き素材から外す。
- 公開切り抜きでは配信者本人の独話部分を優先する。
- 文字起こしリポジトリは Private のまま運用する。

## 3. 動画化ルール

### 3-1. 動画候補の優先順位
1. 独話で成立する
2. オチがある
3. 短く切れる
4. 個人情報リスクが低い
5. キャラクター性が出る

### 3-2. 尺
- 第一候補: 20〜45秒
- 第二候補: 45〜75秒
- 長くても90秒前後
- 2分を超える場合は原則分割する

### 3-3. タイトル
説明ではなく異常事態を一言で言う。

例:
- 遺影をAIでカード化したら破門された
- 神様は毎年ドラフトした方がいい
- 幽霊にも表示バグがある
- うんこマンで教師を辞めた

### 3-4. 仕上げ前確認
- 音声は元配信か
- 字幕は音声に合っているか
- 動画尺は長すぎないか
- オチまで含まれているか
- 個人情報を漏らしていないか
- サムネ・フックが立っているか

---

## 4. 字幕ルール

### 4-1. 逐語字幕
- Whisperやタイムコード付き認識を使う。
- 字幕は聞こえる順序に合わせる。
- ASR由来の不自然な間隔は根拠を持って補正してよい。

### 4-2. 演出テロップ
- 要約テロップを逐語字幕扱いしない。
- 要点整理・フック強化に使う。

### 4-3. 優先度
1. 聞き取れないと意味が崩れる箇所
2. オチ
3. 固有名詞
4. 長い理屈の見出し化

---

## 5. VRM動画ルール

### 5-1. 完成条件
- Tポーズでない
- 腕・姿勢が自然
- 口が実音声に反応して動く
- 字幕またはテロップが意図通り
- 冒頭・中盤・オチの最低3箇所を検品済み

### 5-2. 禁止事項
- 動かないVRM静止画を完成品扱いしない
- 口の動かない既成MP4をループしてごまかさない
- 実同期がないのに「字幕版」と言わない

### 5-3. 口パク
- 音声エンベロープまたは口パク用データで制御する。
- 喋っている箇所で反応していることを確認する。

### 5-4. モーション
- 基本姿勢は自然体。
- 軽い呼吸、瞬き、頭部の揺れは可。
- 意図しない十字架/Tポーズは禁止。

## 7. GitHub保存ルール

### 7-1. 「入れた」の定義
「GitHubに入れた」と言ってよいのは、ファイル作成・更新後に実際に fetch / read して内容を確認した時だけ。

### 7-2. 索引だけで完了扱いしない
- ディレクトリやmanifestが存在するだけでは完了にしない。
- raw本文、clean全文、report本文をそれぞれ確認する。

### 7-3. 複数端末・複数チャット
- 同じファイルを同時編集しない。
- main を正本とし、作業開始時と終了時に最新mainを再読する。
- 別端末の変更が入った場合は上書きせず再取得する。

## 9. 反省の固定化

- できていないものを、できたと言わない。
- 原本と校正版を混ぜない。
- 旧命名を復活させない。
- VRMは実際に動いてから出す。
- 字幕は勘で置かない。
- GitHubは読んで確認してから「入った」と言う。
- ユーザーの指摘を最優先で検証する。
